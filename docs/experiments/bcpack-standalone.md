# Standalone BCPack BC1–BC7 reconstruction

`src/startup_stubs/bcpack_decoder.h` reconstructs the seven BC block formats from
complete BCPack streams. BC2 uses fifteen lanes and BC6H uses sixteen. BC1 now
uses independent endpoint/index references and the full 255-entry initial
dictionary. The old fitted BC1 endpoint window and quadrant masks are removed.
BC6H supports all fourteen modes and changes of precision/subset count across
historical references. The output is packed BC blocks, not RGBA pixels.

The DirectStorage stand-in decodes into a temporary buffer and publishes it
only after the complete request succeeds. BC2/BC6H no longer return successful
blank textures. An invalid format or malformed stream fails. Existing file,
memory, outer RFC 1950 zlib and physical-page destination handling applies.
Historical `bcpack-blank` counters remain in the log schema for compatibility;
this decoder does not produce blank-success requests.

## Sources and constants

The entropy decoder and existing BC3/4/5/7 code retain their bcpack-rs and
silicon-rans notices in [THIRD_PARTY_NOTICES.md](../../tools/_bcpack_rans/THIRD_PARTY_NOTICES.md).
The new BC1/2/6H routines are original C++ reconstruction code. Research used
the installed GDK interface, local implementation inspection, and comparisons
with public bcpack-rs and VIctory implementations. This is not a claim of a
strict clean-room process. No GPL implementation or binary table blob was
copied into these files.

`bcpack_tables_extra.inl` contains fixed format dictionaries and rank mappings.
They were reconstructed by sending chosen, entirely synthetic lane streams to
the developer oracle's `BCPackDecompress` API and reading the resulting standard
BC fields. There is no sample fitting, approximation, per-asset lookup or
run-time learning. The recovery tool does not read the DLL's data section.

The BC6H wire descriptors adapt Microsoft's MIT-licensed
[DirectXTex BC6HBC7.cpp](https://github.com/microsoft/DirectXTex/blob/a8e5dbf42909aeeb9fcf9c2ae399ae3c06737379/DirectXTex/BC6HBC7.cpp),
revision `a8e5dbf42909aeeb9fcf9c2ae399ae3c06737379`, SHA-256
`187434fab12351df0f875ae09390981034e8479159a6f4aaaf0904f007182b8a`.
The emitted BCPack blocks use ascending high base-endpoint bits in modes 13/14;
the descriptor generator applies that ordering explicitly. Preserve the
DirectXTex MIT notice when redistributing those descriptors.

Normal builds, tests and runtime DLLs require neither GDK nor BCPack.dll.
The optional oracle target and script below are development tools only. They
require a separately installed developer oracle, which is not redistributed.

## Reproduce the public checks

From an x64 Visual Studio developer PowerShell:

```powershell
. ./tools/dev.ps1
cmake --preset dev
cmake --build --preset dev --target bcpack_formats_check startup_stub_consumer startup_stub_xcrdapi
ctest --preset dev --no-tests=error -R '^(bcpack_all_formats|startup_bcpack_storage)' -V
python -B tests/bcpack_tables_check.py
```

The golden test generates 12,330 synthetic streams from source. It checks all
255 initial references plus the zero predictor, independently selected endpoint
and index references, all fourteen BC6H modes and all 32 partitions. Random
symbol streams cover all seven formats and block counts 2, 17, 255, 256, 257
and 1024, including mode changes and history-ring wrap. BC7 selects all 285
mapped controls. Every supported entropy path must reproduce the same bytes.

Each group is checked against a fixed FNV-1a-64 hash of the independent oracle's
complete output. The expected hashes are not generated by the decoder under
test. A one-byte mutation must fail the golden control. Truncation, wrong output
alignment, nonzero trailing data and invalid formats must fail with zero bytes
reported. An undefined BC6H mode must fail too. The storage test checks full BC2
and BC6H destination bytes against fixed synthetic oracle outputs across
memory/file, raw/zlib and linear/cross-page requests. Missing page grants, unsupported formats and a bad final BC6H mode after
three valid blocks must preserve the destination; a following valid request
must still succeed.

The unchanged `synthetic_11` BC1 input in `startup_stub_consumer.cpp` had 491
wrong bytes in its former 512-byte expected output. Its first eight expected
bytes were `85 31 64 d5 af be ff bf`; the oracle returns
`8d 73 0a 07 ea b8 fa be`. The fixture now checks the oracle's complete 512
bytes, keeping the original input, size and malformed-input controls.

## Optional oracle reproduction

For the original experiment the installed BCPack library reported version
`1.2603.3.0`. Its binaries, private headers and title payloads are not part of
this repository. Supply paths to your own local installation and to the public
DirectXTex source pinned above:

```powershell
cmake --build --preset dev --target bcpack_oracle_bridge
./out/build/dev/bcpack_formats_check.exe --oracle 'C:/path/to/BCPack.dll'
python -B tools/bcpack_recover_constants.py `
  --sdk 'C:/path/to/BCPack.dll' `
  --bridge out/build/dev/bcpack_oracle_bridge.dll `
  --bc6-reference out/DirectXTex/DirectXTex/BC6HBC7.cpp `
  --output out/bcpack_tables_extra.inl `
  --storage-goldens out/bcpack_storage_goldens.h
python -c "from pathlib import Path; assert Path('src/startup_stubs/bcpack_tables_extra.inl').read_text() == Path('out/bcpack_tables_extra.inl').read_text()"
python -c "from pathlib import Path; assert Path('tests/bcpack_storage_goldens.h').read_text() == Path('out/bcpack_storage_goldens.h').read_text()"
```

The recovery script queries each dictionary entry separately. BC1/2 ranks are
recovered with zero predictors. BC6H's base endpoint uses the sixteen-bit mode;
the other endpoints use modes exposing their complete stored precision. The
generated table file reproduced LF-normalized SHA-256
`181f279bbc84a3e93aa4d44bf6f7c6e522493b3a92538b7209e4b22721a3a12e`.
An oracle change may change output; investigate differences before replacing
goldens or format constants.

## Local comparison and limits

A separate read-only comparison covered 105,845 chunks from 45 local archive
pools, totaling 16,356,958,208 decoded bytes. Every chunk was compared byte for
byte with the installed oracle on the AVX2 path. A distributed sample of 882
chunks also used the reference and scalar paths. There were no byte mismatches
or guard violations. No archive bytes or extracted textures are included here.

| Format | Local archive chunks |
|---|---:|
| BC1 | 100,020 |
| BC2 | 0 |
| BC3 | 35 |
| BC4 | 77 |
| BC5 | 325 |
| BC6H | 268 |
| BC7 | 5,120 |

An additional 312 oracle-compressed synthetic cases across BC1–BC7 matched
byte for byte on all three paths, including random, repeated and historical
blocks and individual BC6H/BC7 modes. Inputs rejected by the oracle compressor
were excluded from that successful-compression count, not called passes.
The public synthetic golden suite supplies BC2 coverage independently of the
local archives. These are packed-block decoding checks, not GPU image or
full-application startup measurements. Finite test coverage cannot establish
correctness for every possible stream.
